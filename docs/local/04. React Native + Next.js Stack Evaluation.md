# **Architecture Evaluation: Universal Cross-Platform Development with React Native and Next.js**

A strategic assessment of uniting React Native for Web and Next.js to achieve unified UI codebases across web and mobile platforms.

# **Architectural Overview**

Historically, cross-platform engineering has required a structural compromise: either build web applications wrapped in native WebViews (e.g., Capacitor, Cordova), or develop mobile applications using cross-platform native primitives while maintaining a separate, dedicated web codebase.

The combination of **Next.js** and **React Native** (enabled by `react-native-web`) shifts this paradigm. Rather than treating the web as an afterthought inside a mobile shell, this architecture takes a **web-first approach** while delivering native rendering on iOS and Android.

## **Structural Topology**

The stack relies on a multi-layer abstraction pipeline structured within a unified monorepo:

* **Presentation Layer (React Native Primitives):** Components are authored against core React Native primitives (`<View>`, `<Text>`, `<Pressable>`, `<Image>`). These components are decoupled from both DOM elements and mobile platform binaries.  
* **Transpilation Layer (`react-native-web`):** For the web target, `react-native-web` maps React Native primitives to DOM elements and generated CSS, using semantic HTML when role and aria props are set. Mobile targets run on React Native’s Hermes engine.  
* **Application Shell (Next.js & Native Runtimes):** Next.js serves as the application shell for web delivery, handling Server-Side Rendering (SSR), Incremental Static Regeneration (ISR), static asset optimization, and edge routing. In parallel, Expo or bare React Native acts as the execution host for iOS and Android binaries.

| Architectural Layer | Web Target | iOS / Android Targets |
| :---- | :---- | :---- |
| **Execution Host** | Next.js (Node.js runtime / Edge) | Expo SDK / React Native Runtime |
| **Layout & Primitives** | `react-native-web` → DOM (`div`, `span`) | Yoga Layout → UIKit / Android Views |
| **Styling Engine** | Scoped CSS rules / atomic CSS injection | JSI Native Style Maps / StyleSheet |
| **JS Engine** | V8 / JavaScriptCore / SpiderMonkey | Hermes Engine |
| **Navigation** | Solito → Next.js App Router (File-based) | Solito → React Navigation (Native Stacks) |

# **Architectural Advantages (Pros)**

## **1\. Unified Design System & High Shared UI Coverage**

By using React Native primitives as the single source of truth, teams eliminate duplicate component implementations. A single button, modal, or complex data table component lives once in a shared package. This prevents divergence between mobile and web design languages, reduces surface area for bugs, and shrinks feature delivery time across platforms.

## **2\. Server-Side Rendering (SSR) & SEO**

Traditional cross-platform frameworks struggle with web discoverability because they render entirely on the client (SPA model). Next.js provides server-side rendering for `react-native-web` output. Server-rendered HTML is served directly to search engines and web crawlers, which supports good Core Web Vitals, including Largest Contentful Paint (LCP), and search indexing when the app is built with performance in mind.

## **3\. Native Mobile Performance**

Unlike hybrid WebView solutions, mobile platforms execute directly through the JavaScript Interface (JSI) into native UI components via the New Architecture (Fabric renderer and TurboModules). The application executes against the optimized Hermes runtime, which supports 60/120 FPS transitions and animations on capable devices, with native touch handling.

## **4\. Consolidated Developer Velocity & Shared Business Logic**

State management (e.g., TanStack Query, Zustand), utilities, analytics tracking, and domain-layer validation logic (e.g., Zod) can be shared across platforms with little or no modification. Frontend and mobile teams can work as one cross-functional platform team, which reduces team fragmentation and hiring overhead.

# **Architectural Trade-offs & Complexities (Cons)**

## **1\. Monorepo and Tooling Overhead**

Orchestrating Next.js, Metro (the React Native bundler), and shared packages in tools like Turborepo or Nx introduces non-trivial build system friction. Transpiling TypeScript monorepo packages, hoisting dependencies, managing conflicting lockfiles, and synchronizing Babel or SWC plugins require ongoing build maintenance.

## **2\. Disparate Routing Paradigms**

Next.js relies on URL paths and document-based navigation models, whereas native mobile uses view-stack mechanics (push, pop, modal presentation cards, tab managers). Reconciling these mental models across platforms often requires abstraction layers or maintaining parallel routing directories (e.g., Next.js `app/` directory alongside React Navigation configurations).

## **3\. Third-Party Dependency Incompatibilities**

The broader npm ecosystem typically targets either DOM runtimes or native mobile environments. Libraries depending on DOM-specific properties (`window`, `document`, SVG DOM manipulation) crash mobile builds without custom polyfills. Conversely, native modules with native bindings (`.swift`, `.kt`) will fail in Next.js builds unless properly shimmed or isolated using platform-specific file extensions (.web.ts vs .native.ts).

# **Future Blockers & Mitigation Strategies**

`Platform Codebase`  
  ├── Shared Domain & Primitives (React Native)  
  │     ├── Native Compilation ──\> Native JSI (iOS / Android)  
  │     └── Web Compilation (Tamagui) ──\> Extracted CSS (Next.js)

  └── Routing Bridged via Solito

## **1\. React Server Components (RSC) and Native Boundary Parity**

* **The Blocker:** The Next.js App Router uses React Server Components by default. However, React Native apps render on the client, and React Server Components support for native apps is still experimental in Expo. This disparity can lead to code that runs smoothly on Next.js SSR but requires heavy mocking or refactoring to work on mobile clients.  
* **Mitigation:**  
  * Adopt **Solito** to share navigation code between the Next.js App Router on web and React Navigation or Expo Router on native.  
  * Clearly isolate server-only operations (`import 'server-only'`) and design components around strict Client Boundary contracts (`'use client'`), so shared component trees behave consistently across Next.js and client-driven native architectures.

## **2\. CSS-in-JS Runtime Overhead on Web**

* **The Blocker:** Classic `react-native-web` styling serializes styles at runtime, injecting dynamic CSS rules into the document head. While acceptable for modest layouts, dynamic runtime style computation can add main-thread overhead under heavy DOM updates and can affect Interaction to Next Paint (INP), the Core Web Vitals metric that replaced First Input Delay (FID) in March 2024\.  
* **Mitigation:**  
  * Adopt a build-time styling approach such as Tamagui (an optimizing compiler for web and native) or NativeWind (Tailwind-based).  
  * Tamagui extracts styles into atomic CSS at build time for the web and maps them to native styles on iOS and Android, which reduces runtime style work on the web. StyleX is web-first, and its native support through React Strict DOM is experimental.

## **3\. Deep Linking and Universal State Synchronization**

* **The Blocker:** Synchronizing nested native stack states with browser history and deep links creates brittle synchronization issues if native screens deviate from browser URLs.  
* **Mitigation:**  
  * Implement unified navigation and deep linking contracts using **Solito's** navigation API alongside centralized URI mapping specifications.  
  * Treat the URL as the single source of truth for deep application state on both native and web environments, allowing route changes to deterministically dictate UI state across view hierarchies.

# **Production Evidence and Documentation**

Each major part of this stack is documented by its maintainers, and the parts run in production apps. Public evidence for one shared UI codebase between Next.js and React Native in a named, large product is thinner than for the individual parts, so each example below states what it shows.

* [Solito](https://solito.dev/) is a small wrapper around React Navigation and Next.js that shares navigation code, together with patterns and examples for building cross-platform apps with React Native and Next.js. [Version 4](https://solito.dev/v4) added support for the Next.js App Router, and its [compatibility page](https://solito.dev/compatibility) lists versions tested together (Next.js 16, React 19.1, Expo SDK 54, React Native 0.81 or 0.82). Solito's creator, Fernando Rojo, is [Head of Mobile at Vercel](https://vercel.com/blog/how-we-built-the-v0-ios-app). According to [Callstack's recap](https://www.callstack.com/events/exploring-solito-5-building-cross-platform-apps-with-react-and-react-native) of a talk by Rojo, Solito 5 takes a web-first approach in which the web app renders plain HTML and Next.js components instead of react-native-web.  
* [Tamagui](https://tamagui.dev/) is a universal UI kit, style system and optimizing compiler for React Native and web. Its [create-tamagui starter](https://tamagui.dev/docs/guides/create-tamagui-app) combines Expo, Expo Router, Solito and Next.js, including both the pages and app directories, and its [Next.js guide](https://tamagui.dev/docs/guides/next-js) covers Pages Router and App Router setups. The free starter repository now recommends [Takeout](https://takeout.tamagui.dev/docs/tamagui) as the more actively maintained starter.  
* [react-native-web](https://necolas.github.io/react-native-web/docs/about-project) is documented as used in production web apps by companies including Meta, Twitter and Flipkart. [Curai Health](https://curaihealth.com/blog/using-react-native-for-web-in-production-at-curai) also published an account of running it in its production medical chat app.  
* [Bluesky](https://github.com/bluesky-social/social-app)'s official app for web, iOS and Android is a single React Native and TypeScript codebase, with a small Go service that serves the react-native-web build. It shows one UI codebase on all three targets, but it is built with Expo and react-native-web, not Next.js.  
* Vercel's v0 for iOS, the company's first mobile app, was built with React Native and Expo after several stack experiments. [Vercel's write-up](https://vercel.com/blog/how-we-built-the-v0-ios-app) and a [Callstack interview](https://www.callstack.com/podcasts/building-v0-ios-and-fixing-react-native-along-the-way) with its engineers describe a native-feeling chat interface built with Reanimated and LegendList, custom native modules, and fixes contributed back to React Native. This supports the native-quality claim; the sources reviewed here do not describe it as a Solito-style shared UI codebase.  
* Agency reports: [Theodo's technology radar](https://apps.theodo.com/en/radar/react-native) says its teams use either Expo Router or Solito depending on the project, and names Solito's main advantage over Expo Router as access to advanced Next.js features. [Bothrs](https://www.bothrs.com/story/how-we-build-native-web-apps-using-the-same-codebase), a product studio, describes building web with Next.js and mobile with Expo, joined by Solito, and claims about 95% shared code; that figure is the vendor's own claim, not an independent measurement.  
* [Expo Router](https://docs.expo.dev/router/web/server-rendering/) adds file-based routing and web output to Expo apps. Expo documents static and server rendering for web, and its [React Server Components](https://docs.expo.dev/guides/server-components/) support is labeled experimental and in beta. It is the main alternative to Next.js plus Solito when one framework should cover all targets.

# **Adoption Options and Fallbacks**

The primary recommendation is Next.js with React Native through Solito. Two lower-risk alternatives exist for teams that prefer fewer niche dependencies. A short pilot on one feature can compare the options on the same measures: percent of code shared, web performance and build time.

* **Option A, Next.js plus Solito (primary):** best web SEO and server rendering, with shared navigation and UI. It adds Solito and, optionally, Tamagui as dependencies, and it needs monorepo tooling that works for both Next.js and Metro.  
* **Option B, Expo Router on every platform:** one framework and one router for web, iOS and Android, with no Solito. [Expo documents static and server rendering for web](https://docs.expo.dev/router/web/server-rendering/), but its server features are newer than Next.js, so web SEO and rendering control are weaker.  
* **Option C, separate Next.js and React Native apps with shared packages:** only logic such as API clients, validation and state is shared. It carries the lowest risk and is the most common setup, but UI is built twice. It can also be a first step toward Option A or B.

## **Repository Evidence**

These public repositories show each approach in code. The first is a production app. The others are starters and examples, not production evidence.

* [**bluesky-social/social-app**](https://github.com/bluesky-social/social-app)**:** Bluesky's production app for web, iOS and Android, built as one React Native and Expo codebase. It shows one UI codebase on all three targets, without Next.js.  
* [**tamagui/starter-free**](https://github.com/tamagui/starter-free)**:** a monorepo starter that combines Expo, Solito, Next.js and Tamagui. Its maintainers now recommend Takeout as the more actively maintained starter.  
* [**nandorojo/solito**](https://github.com/nandorojo/solito)**:** the Solito repository, with example monorepos that share screens and navigation between Next.js and Expo.  
* [**expo/examples**](https://github.com/expo/examples)**:** Expo's official examples, including Expo Router projects for iOS, Android and web.  
* [**georga-app/georga-client-solito**](https://github.com/georga-app/georga-client-solito)**:** a public project that uses Solito, which shows it outside a starter template.
